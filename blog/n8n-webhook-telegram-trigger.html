n8n Webhook to Telegram: The Only Trigger You Actually Need

2026-09-24 · 7 min read

The Telegram Trigger node is the piece you need when a Telegram message should start an n8n workflow — not a generic webhook, not a polling loop, not a third-party bridge.

Why the Telegram Trigger node is the one to learn first

If you run n8n and want something to happen when a Telegram message arrives, the Telegram Trigger node is the piece you need — not a generic webhook, not a polling loop, not a third-party bridge. It registers a webhook with Telegram the moment you activate the workflow, so updates reach your n8n instance within seconds and nothing keeps calling the API on a timer. For a solopreneur running one or two automations, that means less infrastructure to maintain and faster reactions when something actually matters.

What the Telegram Trigger actually listens for

The node ships with nine event families. Most people only ever need one or two, but it helps to know the full surface before you start wiring conditions:

  • message — a user sends a text, photo, document, or sticker to your bot or a group the bot is in. This is the default and the most common starting point.
  • callback_query — someone taps a button planted by an inline keyboard. Use this when your workflow offers choices (approve, deny, pick a template) and you want the tap to route somewhere.
  • channel_post — a post lands in a channel the bot is a member of. Useful for monitoring a broadcast channel or auto-responding to new posts.
  • edited_message — a message was edited after send. Handy when you want to catch corrections or updates without treating them as brand-new messages.
  • edited_channel_post — same idea, but for channel posts.
  • inline_query — a user typed your bot name in the Telegram input bar and selected it. This is the entry point for bots that surface results as the user types.
  • shipping_query, pre_checkout_query, poll — niche events for payments and polls; most solopreneur workflows never touch these.

Pick the events you actually care about on the node's parameter panel, activate the workflow, and n8n handles the rest. You do not need to manually register a webhook URL or keep a tunnel running unless you are testing locally.

The one-time setup that everything else depends on

Before any workflow can fire, you need a Telegram bot and a credential in n8n. The whole sequence is short enough to do in a single sitting:

  • Open Telegram and talk to @BotFather. Send /newbot, pick a name and a username ending in bot, and copy the API token BotFather hands back.
  • In n8n, open the Credentials menu, create a Telegram credential, and paste that token into the Access Token field. One credential covers every workflow that needs Telegram — you do not create a new one per bot or per workflow.
  • Add a Telegram Trigger node to a fresh workflow, select the credential, choose the event (usually message to start), and activate the workflow.

When the workflow activates, n8n registers the webhook with Telegram behind the scenes. From that point on, any message that matches your chosen event type flows into the workflow as JSON. The first time you test it, send a message to the bot and confirm an execution appears in the n8n execution list — that single confirmation is worth more than any tutorial screenshot.

Local testing and the HTTPS requirement

Telegram only calls webhook URLs over HTTPS. That is fine on n8n Cloud, where the instance already has a public HTTPS address. On a self-hosted instance running on your laptop or a home server, you need a public URL for the registration to stick. The common approaches:

  • ngrok — forwards a public HTTPS URL to your local n8n port. Set WEBHOOK_URL and WEBHOOK_TUNNEL_URL to the ngrok address so n8n registers the right endpoint with Telegram.
  • Pinggy — a lighter-weight alternative that gives you a public tunnel without an account in many cases; useful for a quick local test session.
  • A VPS or always-on host — once a workflow is more than a test, running n8n on a small server removes the tunnel entirely and keeps the webhook stable across restarts.

If the webhook registration fails, the most common cause is an HTTP URL where Telegram expected HTTPS. Check that your tunnel or public host is serving HTTPS and that n8n's WEBHOOK_URL points to it.

A practical first workflow: sales alerts in Telegram

The pattern that justifies learning the trigger node on day one is a Gumroad-to-Telegram notifier. The flow is simple enough to build in under ten minutes and immediately useful:

  • Gumroad sends a webhook ping to an n8n webhook node when a sale lands.
  • An intermediate step formats the buyer name, product, and amount into a short message.
  • A Telegram node sends that message to a private channel or your personal chat.

This is the same shape as most notification automations — inbound event, light formatting, outbound alert — and it teaches you the credential flow, the trigger-vs-webhook distinction, and how to pass data from one node to the next without taking more than a coffee break. What to wire next once the trigger works

Once a message reaches your workflow, the Telegram node can do more than send a plain reply. A few directions that tend to pay off for solo operators:

  • Inline keyboards — attach buttons to a message and let users tap through choices instead of typing commands. The callback_query event catches the taps.
  • Group monitoring — add the bot to a group, set it to admin if it needs to read every message, and react to keywords, links, or join/leave events.
  • Conditional routing — an IF node on the incoming message text or chat ID lets one workflow handle multiple intents: help commands go one way, purchase alerts another, unknown messages a third.
  • Scheduled follow-ups — pair the trigger with a Cron node so the bot sends a reminder, a digest, or a status update on a timer rather than only reacting to inbound messages.

None of these require custom code. The Telegram node covers sending messages, replying to the originating chat, and attaching keyboards; everything else is standard n8n logic layered on top.

The mistakes that burn the most time

A few things to avoid so the setup stays a twenty-minute task instead of a weekend:

  • Re-registering the webhook by hand — the Trigger node does this on activation. Manually calling Telegram's setWebhook alongside an active n8n workflow creates conflicts and dropped updates.
  • Using the wrong credential — the Telegram Trigger and the Telegram sending node both want the same bot token credential. If you created one per workflow by habit, consolidate to a single credential and re-select it everywhere.
  • Testing HTTP locally and assuming production is the same — a local HTTP tunnel works for a test session, but the production webhook must be HTTPS. If you ship a workflow that registrations fails on in production, the first thing to check is the protocol.
  • Over-triggering on every event — selecting all nine events on the node "just to see what happens" fills your execution log with noise. Start with message, add only the events you actually route on, and ignore the rest.

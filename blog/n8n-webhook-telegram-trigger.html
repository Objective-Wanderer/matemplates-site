n8n Webhook to Telegram: The Only Trigger You Actually Need

Aug 31, 2026 · 6 min read

Email gets buried, polling wastes cycles. A Telegram webhook lands where your eyes already are — here's the whole setup, plus the gotchas that bite you in production.

Why webhooks beat polling and email

Email notifications get buried. Polling wastes cycles checking for updates that haven't happened. A Telegram webhook does the opposite — the event comes to you, instantly, and your phone lights up.

I use this pattern for sale alerts, server pings, and client onboarding updates. Zero compute while idling, sub-second delivery, and the whole thing runs on free-tier n8n.

Two ways to wire it in n8n

You've got two paths:

  • Generic Webhook node — n8n gives you a static HTTPS endpoint. External services (Gumroad, Stripe, your own API) POST data there, you parse the JSON, and forward a formatted message to Telegram via the sendMessage node. This is what I use for most one-way alerts.
  • Telegram Trigger node — n8n registers its own webhook URL with Telegram's setWebhook API automatically. When someone messages your bot or fires a /status command, Telegram pushes the update straight into your workflow. Better for two-way bots.

For sale notifications, support pings, or monitoring alerts — the Generic Webhook route is simpler and more predictable. You control exactly what hits the endpoint.

Set up your bot with BotFather

You need a bot token first. Takes two minutes:

  • Open Telegram, message @BotFather.
  • Send /newbot, pick a display name and a username ending in bot.
  • Copy the token (looks like 123456789:ABCdefGhIJKlmNoPQRsTUVwxyZ). Paste it into n8n's Telegram credentials.
  • If the bot lives in a group, send /setprivacy → Disabled so it can actually read messages.

The n8n setup

Telegram only accepts webhooks over HTTPS. If you're self-hosting n8n, make sure you've got a valid domain with a reverse proxy (Caddy, Nginx, Cloudflare Tunnel — whatever you run) and the WEBHOOK_URL env var pointing at it.

On the canvas:

  • Credentials: paste your BotFather token into the Telegram API credentials.
  • Test vs Active: the Telegram API allows only one webhook per bot. When you click "Listen for Test Event", n8n registers a temporary one. Flip the workflow to Active to lock in the production endpoint — this is the one that stays up.
  • Parsing the payload: message text lives at {{ $json.message.text }}, sender info at {{ $json.message.from }}. That's all you need for most alerts.

Things that bite you in production

Three gotchas I learned the hard way:

  • Markdown escaping: underscores, asterisks, and angle brackets in dynamic text cause 400 Bad Request from Telegram. Sanitize before you build the message. A Code node with a simple replace-all works.
  • Rate limits: Telegram caps you at 30 messages/sec across all chats, 1/sec per group. For high-volume triggers, batch messages or add a small delay between sends.
  • Duplicate alerts: if Telegram doesn't get a 200 OK back quickly enough, it retries. Keep your trigger workflow lightweight so it responds fast — otherwise you get the same alert twice.
